Engineering Protocol — Draft v0.1 Kudos Platform

The PR is the plan.

Open the pull request before you write the code. The body carries the task queue, each item collapses into its own evidence, and nothing gets checked off until that section is actually finished. When a reviewer arrives, the plan and the diff are the same document.

Applies to api · web · ledger · infra Order Why → How → Queue → Risk Enforced by pr-body-check CI
01

Why draft first

A PR description written after the fact is a summary. A PR description written before the fact is a contract — and the diff either honors it or doesn't.

One artifact
The ticket, the implementation plan, the test log and the review notes stop living in four tools. The reviewer reads one page and can trust it, because it was updated as the work happened, not reconstructed at the end.
Scope lock
The queue is written when the change is still cheap to argue about. A task appearing mid-flight is visible as an edit to the body — scope creep becomes an event, not a surprise in the diff.
Incremental writing
Nobody writes a 900-word description at 6pm on Friday. You write forty words per section, at the moment you finish that section, while the detail is still in your head.
Reviewable state
Anyone can see how far along the change is without asking. 6/9 done · 1 blocked beats a Slack thread that says "almost there".
02

The lifecycle

Five stages. The PR exists for four of them before a reviewer is ever asked to look.

STAGE 1

Open empty

Branch, one throwaway commit, draft PR. The template loads. Fill in Why only — if you can't, the work isn't ready to start.

draft
STAGE 2

Write the queue

Decompose into tasks with owners and exit criteria. Everything starts unchecked. Mark conditional sections required or not-applicable now, with a reason.

draft
STAGE 3

Fill as you go

Finish a task, expand it, write the evidence inside it, then check the box. Push. The body and the branch move together.

draft
STAGE 4

Close the queue

All items done, skipped with a reason, or moved out to a follow-up issue that is linked. Risk score computed and pasted.

ready
STAGE 5

Review the record

Reviewer reads the body top-to-bottom first, diff second. Review comments land as new queue items, not as loose threads.

in review
03

Anatomy of the body

Ordered for the reader, not the writer: intent before mechanism, mechanism before proof, proof before risk. Conditional sections are declared at the top of the queue so a docs-only PR never types "N/A" nine times on autopilot.

SectionAnswersRequired
Why What breaks or stays broken if we don't merge this? Links the ticket, states the user-visible outcome in one paragraph. always
How The approach in 3–6 sentences, plus what you rejected and why. The reviewer's map before they read a diff. always
Task queue The plan as checkboxes. Each item collapses to owner, exit criteria, evidence, and files touched. always
Verification What you ran and what it proved. Commands, environments, and one line on what is not covered. always
Security Authn/authz paths touched, PII or card data in scope, new inputs and how they're validated, secrets handling, new dependencies. if triggered
Performance Query plans for new or changed SQL, N+1 risk in GraphQL resolvers, payload size delta, before/after numbers with the measurement method. if triggered
Data & migrations Forward and backward plan, row counts, lock behavior, backfill duration, whether the migration is safe to run before the deploy. if triggered
Observability The metric, log or trace that tells you this worked in prod — and the alert that fires when it stops. if triggered
Risk & rollback The computed score, the flag or config that turns it off, and who to page. Always present because every change has a score, even a 0. always

Trigger rules, not judgment calls: Security is required when the diff touches auth, a public resolver, a secret, PII/PAN, or adds a dependency. Performance when it touches SQL, a hot resolver, a loop over a network call, or a lambda in the request path. Data when a migration file changes. Observability when a new code path can fail silently.

04

The task queue, live

Each item is a collapsed <details> block. Collapsed, the queue reads as a status board in ten seconds. Expanded, an item carries everything a reviewer would otherwise have to ask for. Click a box to cycle its state; click a row to expand it.

[ ] queued — written, not started [~] in progress — one at a time, ideally [x] done — code merged to branch and evidence written [!] blocked — reason and unblocker named inside [-] dropped — with a reason or a linked follow-up
Draft #4127 · feat(rewards): per-issuer offer caps in the optimizer marcjimenez wants to merge 11 commits into main

Why

Chase and Amex both cap category bonuses per quarter, and the optimizer currently recommends cards past their cap — users see a "5% back" recommendation that pays 1%. Support has taken 34 tickets on this in six weeks (KUD-2210). This adds per-issuer caps as a first-class constraint so a capped card drops out of the ranking instead of being silently wrong.

How

Caps live in a new issuer_offer_cap table keyed by (issuer, category, period), loaded once per optimizer run and applied as a filter in the scoring pass rather than as a post-hoc adjustment — a capped card should never enter the ranking, not be removed from it. Rejected: computing caps inside the GraphQL resolver (would have added a per-card query, N+1 on a hot path), and storing remaining balance per user (correct but needs a nightly reconciliation job we don't have yet).

05

Risk assessment score

Five factors, weighted, scored 0–24. The point isn't precision — it's that two engineers scoring the same PR land in the same band, and the band decides the review requirements instead of a hallway conversation. Score once when the queue closes, paste the line into the body.

    Low0–4One reviewer. Merge on green. No extra sections.

    Elevated11–16Two reviewers, one outside the pairing. Feature flag required. Rollback rehearsed, not just described.
    High17–24Two reviewers plus the domain owner. Staged rollout with a named % schedule. Deploy in business hours with an owner online.
    06

    Making it stick

    A template without a check is a suggestion. Four rules, all mechanical, all cheap — every one of them can fail a status check rather than a human's patience.

    queue-closed

    Blocks "ready for review" while any item is [ ] or [~]. [!] and [-] pass only if the block has a Blocked by or reason line.

    sections-triggered

    Diffs the changed paths against the trigger rules. Touched a migration with no Data section? Failing check, with the file that triggered it named in the output.

    score-present

    Requires a RISK: n/24 (band) line whose factor breakdown parses. Elevated and High also require a flag name and a rollback line.

    body-drift

    Warns (never blocks) when commits land after the last body edit — the signal that the record and the branch have drifted apart.

    Every checkbox in the template is verifiable in under thirty seconds. "Code follows best practices" is not a checkbox; "existing tests pass locally" is.
